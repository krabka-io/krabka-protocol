# RUSTSEC-2023-0071 (rsa Marvin attack) reachability

[RUSTSEC-2023-0071](https://rustsec.org/advisories/RUSTSEC-2023-0071) is a
timing side channel in the `rsa` crate's PKCS#1 v1.5 private-key decryption.
An attacker who can time many decryptions can recover the plaintext. No
patched `rsa` release exists.

## Where `rsa` comes from

`rsa 0.10.0-rc.18` enters this workspace on one path:

```text
krabka-security (feature "gssapi")
└── krabka-sspi 0.23.0
    ├── rsa 0.10.0-rc.18
    └── picky 7.0.0-rc.26
        └── rsa 0.10.0-rc.18
```

`rsa` and `picky` are hard dependencies of `krabka-sspi`. The only way to keep
`rsa` out of a build is to leave `krabka-sspi` out, so `krabka-security` makes
it optional behind the `gssapi` feature:

- `gssapi` is not in `default`, and no crate in this workspace turns it on.
  `krabka-metadata` depends on `krabka-security` with default features.
- `sspi` stays a native-only dependency. On `wasm32` the feature does nothing.
- A crate that needs Kerberos opts in, with
  `krabka-security = { version = "…", features = ["gssapi"] }`. Downstream,
  krabka-client-rs forwards the feature from its client crates, and
  krabka-broker turns it on where it serves or initiates GSSAPI.

A default build compiles no `rsa` code at all, so the advisory does not apply
to it. The rest of this document covers a build with `gssapi` on.

## Why a `gssapi` build does not reach the vulnerable operation

The advisory needs an RSA private key and an attacker who can submit
ciphertexts for PKCS#1 v1.5 decryption with it. Krabka's GSSAPI code supplies
neither.

**Acceptor (broker side).** `gssapi::provider::SspiAcceptor` reads the
service keytab, keeps only `aes256-cts-hmac-sha1-96` (enctype 18) entries, and
hands those symmetric keys to the sspi Kerberos acceptor through
`ServerProperties`. A client's SASL/GSSAPI tokens reach Kerberos AP-REQ
processing, which decrypts the ticket with the AES service key. They cannot
select another SSPI package or make the acceptor load an RSA key.

**Initiator (client side, and broker to broker).**
`gssapi::provider::SspiInitiator` reads the client principal's
`aes256-cts-hmac-sha1-96` key from a keytab and builds a
`sspi::KeytabIdentity`. The sspi Kerberos client then runs the AS and TGS
exchanges with that symmetric key. It never builds password, smart-card or
certificate credentials, so the KDC replies it decrypts are AES-encrypted
Kerberos messages, not RSA ciphertexts. The KDC transport (`network_client`)
talks TCP to the KDC, or HTTPS through rustls with the `ring` provider. TLS
verifies RSA signatures with a public key through `ring` and `webpki`; it does
not use the `rsa` crate's private-key decryption.

**What does use RSA private keys.** In sspi and picky, RSA private-key
operations belong to PKINIT, PKU2U, smart-card logon and certificate-key
credentials. No Krabka code constructs those, and no Kafka configuration in
Krabka exposes them.

So in both directions the vulnerable decryption is compiled in but never
called, and a remote peer cannot steer a call into it.

## The guards

- **No `rsa` in default builds.** The `rsa reachability` job in
  `.github/workflows/ci.yml` runs `cargo tree -i rsa -e normal` over the
  workspace with default features and fails if `rsa` is in the graph. It also
  checks that, with `--features krabka-security/gssapi`, the only parents of
  `rsa` are `krabka-sspi` and `picky`. A new parent means a new path that this
  analysis has not covered.
- **Advisory scan.** The same workflow runs `cargo deny check advisories`. The
  `RUSTSEC-2023-0071` ignore in `deny.toml` exists only because `deny.toml`
  resolves the graph with every feature on, which includes `gssapi`.

## When this analysis stops holding

Review it again, and do not extend the ignore, if any of these happens:

- Krabka code builds an sspi credential other than a keytab key, such as a
  password, a certificate or a smart card.
- Krabka enables PKINIT, PKU2U, Negotiate or another SSPI package.
- `rsa` gains a parent other than `krabka-sspi` and `picky`, or a `default`
  build pulls it in again.

Drop the feature gate's security rationale, the `deny.toml` ignore and the
`cargo tree` guard once `krabka-sspi` offers a Kerberos-only feature without
`rsa`, or a patched `rsa` release ships.

krabka-broker keeps the broker-side version of this review in
[`docs/operations/security/rustsec-2023-0071.md`](https://github.com/krabka-io/krabka-broker/blob/main/docs/operations/security/rustsec-2023-0071.md),
guarded by `aspect check-rustsec-2023-0071`.
